# Дизайн: админка, наценка/валюта, группировка выдачи и UX

**Дата:** 2026-06-24
**Статус:** утверждён к реализации
**Проект:** api.optparts.kz (NestJS 10 + TypeORM + PostgreSQL, test-frontend)

## Цель

Добавить административный слой и довести UX агрегатора: управление партнёрами и
наценкой, конвертация валют в тенге, единая группировка предложений в карточки,
контроль количества в корзине по остаткам, права доступа и админ-страницы. **Вся
функциональность доступна по REST API (Swagger)**; `test-frontend` — только потребитель.

## Принятые решения

1. **Где UI:** расширяем `test-frontend/` (vanilla, без сборки, легко удаляемый).
2. **Курс валют:** ручной, задаётся в админке, с буфером %. Хранится в БД.
3. **Корзина:** контроль количества по последнему `count` из живой перепроверки —
   без отдельного запроса к партнёру на каждое изменение (у партнёров лимиты).
4. **Конвейер цены:** сначала конвертация в тенге, затем наценка.
5. **Всё по API:** каждая админ-возможность имеет REST-эндпоинт; UI ничего не делает
   в обход API. Безопасность — на бэкенде (`RolesGuard`), фронт лишь прячет разделы.

## 1. Настройки, валюта, наценка (бэкенд)

Новый модуль `settings/` + доработка `pricing/`.

### 1.1. Таблица `app_settings` (key-value)

```
app_settings:
  key        varchar pk      -- 'DEFAULT_MARKUP_PERCENT' | 'FX_RATES' | 'FX_BUFFER_PERCENT'
  value      jsonb
  updatedAt  timestamptz
```
- `DEFAULT_MARKUP_PERCENT` (number) — глобальная наценка (переезжает из env; env =
  фоллбэк/сид).
- `FX_RATES` (object) — курсы к тенге, напр. `{ "RUB": 5.4, "USD": 480, "KZT": 1 }`.
- `FX_BUFFER_PERCENT` (number) — буфер к курсу, напр. `2`.

`SettingsService` кэширует значения в памяти с коротким TTL и инвалидацией при записи.

### 1.2. Валюта оффера

В `SupplierOffer` добавляется `currency: string` (по умолчанию `'KZT'`). Коннекторы
проставляют:
- Tabys, SHATE-M → `KZT`;
- Rossko → `RUB` (api.rossko.ru);
- Autotrade → из поля `currency` ответа (RUB/KZT).

Опциональный override на партнёре: `suppliers.currency` (если задан — приоритетнее
валюты оффера).

### 1.3. Конвейер цены (`PricingService`, одна точка)

```
rate  = FX_RATES[currency] ?? 1
kzt   = costPrice * rate * (1 + FX_BUFFER_PERCENT/100)
markup = suppliers.markupPercent ?? DEFAULT_MARKUP_PERCENT
sell  = round( kzt * (1 + markup/100) )
```
Конвертация в тенге — **до** наценки. `costPrice` клиенту не отдаётся; менеджеру/админу
отдаём `costPrice` (в исходной валюте) + `currency` + `sellPrice` + маржу.

### 1.4. Эндпоинты (ADMIN)

| Метод/путь | Назначение |
|---|---|
| `GET /api/settings` | Текущие настройки (наценка, курсы, буфер) |
| `PUT /api/settings` | Обновить настройки |
| `GET /api/suppliers` | Список партнёров (есть) |
| `PATCH /api/suppliers/:code` | isActive, markupPercent, currency, config (есть, расширяем) |

## 2. Поиск: матчинг и группировка

`GET /api/search` (есть; дорабатываем нормализацию и гарантию сортировки):
- **Группа (карточка)** = нормализованные `article` + `brand` (trim + upper), чтобы
  «BOSCH»/«Bosch» от разных партнёров склеивались в одну карточку.
- **Оффер в группе** уникален по `supplierCode + offerKey` (offerKey = стабильный
  идентификатор предложения/склада партнёра — это и есть «бренд+артикул+склад»).
- Офферы в группе сортируются: `sellPrice` ↑ → `deliveryDays` ↑ → `count` ↓. Цена уже
  в тенге с наценкой (конвертация §1.3 применяется до сортировки).
- Ответ: `exact[]` и `analogs[]`, каждая группа = `{ article, brand, name, offers[] }`;
  оффер наружу: `offerId, supplierCode, supplierName, sellPrice, deliveryDays, count,
  multiplicity, warehouseId, isAnalog, raw`. `costPrice/currency` клиенту не отдаём.

## 3. Корзина: контроль количества

- `GET /api/cart` (есть; живая перепроверка) — добавляем в позицию `maxQuantity`
  (= `count` из перепроверки).
- `PUT /api/cart/items/:id` — валидация `quantity ≤ maxQuantity` по последнему
  известному `count` (без отдельного запроса к партнёру). При превышении → `400`
  «доступно N шт», не сохраняем. Учитывается `multiplicity` (кратность): количество
  валидируется/округляется по кратности, если > 1.
- Финальная перепроверка на `POST /api/orders` остаётся барьером (если остаток упал
  между правками — позиция недоступна, заказ блокируется).

## 4. Права доступа (RBAC)

Роли уже есть (`ADMIN/MANAGER/USER`), `RolesGuard` работает. Закрепляем:
- **ADMIN** — `/api/settings`, `/api/suppliers` (вкл/выкл, наценка, валюта, курсы).
- **MANAGER+ADMIN** — заказы, под-заказы, refresh-status, retry, возвраты,
  `partner_products`, история поиска.
- **USER** — поиск, корзина, свои заказы.

Эндпоинты помечаются `@Roles(...)`; безопасность — на бэке. Фронт читает роль из
`GET /api/auth/profile` и прячет админ-разделы (только UX).

## 5. Фронтенд (test-frontend, vanilla, удаляемый)

Новые/доработанные страницы (consume только API):
- `admin/suppliers.html` — партнёры: вкл/выкл, `markupPercent`, валюта, статус;
  сохранение → `PATCH /api/suppliers/:code`.
- `admin/settings.html` — глобальная наценка, курсы валют, буфер; → `PUT /api/settings`.
- `index.html` (поиск) — результат как **карточки** (артикул+бренд+название) с таблицей
  офферов разных поставщиков, отсортированных по цене; бейджи «точное/аналог»,
  «в наличии/срок N дн».
- `cart.html` — подсветка изменения цены, «макс. N», неактивный «+» при `maxQuantity`.
- `orders.html` — менеджеру: кнопки «обновить статус / ретрай / возврат».
- Общий минимальный CSS (карточки/таблицы/бейджи) + шапка с навигацией и видимостью
  админ-меню по роли.

Изоляция сохраняется: вся папка `test-frontend/` удаляется одним движением.

## 6. Тестирование

- `PricingService`: конвертация по курсу+буфер, затем наценка; фоллбэк курса = 1;
  округление; `costPrice` не утекает в клиентский ответ.
- `SettingsService`: чтение/запись, дефолты из env, инвалидация кэша.
- Поиск: склейка брендов разного регистра в одну карточку, сортировка офферов по цене
  в тенге (с мок-курсами).
- Корзина: `maxQuantity`, блок `quantity > count` (400), кратность.
- RBAC: ADMIN-эндпоинты недоступны USER/MANAGER (где не положено).
- Коннекторы: проставление `currency` (Rossko=RUB, Tabys/SHATE-M=KZT, Autotrade=из ответа).

## 7. Этапы (укрупнённо)

1. **Settings + Pricing:** таблица `app_settings`, `SettingsService`, `currency` в
   `SupplierOffer` + проставление в коннекторах, конвейер цены (convert→markup),
   `GET/PUT /api/settings`.
2. **Search/Cart доработки:** нормализация склейки брендов + сортировка; `maxQuantity`
   и валидация количества в корзине.
3. **RBAC review:** проверить/проставить `@Roles` на всех админ/менеджер-эндпоинтах.
4. **Frontend:** админ-страницы (suppliers, settings), карточки поиска, доработка
   корзины/заказов, общий CSS, gating по роли.

## 8. Вне scope

- Авто-курс валют (getCurrencyCourse / внешний источник) — сейчас только ручной.
- Cron-поллинг статусов (остаётся «по кнопке»).
- Полноценный отдельный admin-SPA (пока расширяем test-frontend).
- Сложные правила наценки (по бренду/категории/диапазону) — пока % на партнёра +
  глобальный дефолт.
