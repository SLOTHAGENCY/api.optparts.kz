# Улучшение покупательского флоу — дизайн

Дата: 2026-07-07
Репозитории: `front` (React/Vite) + `api.optparts.kz` (NestJS)

## Цель

1. Сделать список офферов («Товары партнёров») читаемым и удобным, включая ручной ввод количества
   и показ максимума к заказу.
2. При оформлении заказа дать ввести получателя, телефон (несколько на пользователя) и адрес «на лету».
3. Прогнать и починить мобильные версии по покупательскому флоу.

## Часть A — Читаемость списка офферов (только фронт)

Файлы: `front/src/components/OfferCard.tsx`, `front/src/components/OffersList.tsx`
(применяется везде, где рендерятся офферы: поиск, VIN, OEM, страница офферов).

1. **Лучшее предложение видно сразу.** В `OffersList` офферы каждой группы сортируются по `sellPrice`
   по возрастанию; самому дешёвому прокидывается `recommended` (бейдж «Выгодно» + подсветка — механика
   в `OfferCard` уже есть, сейчас не используется).
2. **Строки-колонки.** Карточка выравнивается в колонки: поставщик(+бейдж) | срок | наличие | цена |
   количество | кнопка. Меньше вертикального паддинга, ровные колонки для сканирования сверху вниз.
3. **Ручной ввод количества.** Между `−`/`+` — числовое `<input>`: пользователь вписывает точное число.
   На `blur`/Enter значение клампится в `[multiplicity … maxQty]` и округляется до кратности `step`.
   `maxQty = offer.count` (если `count>0`).
4. **Показ максимума.** Рядом с наличием — сколько можно заказать: «10 шт» → при вводе показываем
   «из 10». Кнопки `+`/поле не дают выйти за `maxQty`. При `count===0` — «Под заказ», maxQty не ограничен.
5. **Мобилка.** На `<sm` карточка в 2 ряда: (поставщик + цена) / (срок·наличие + степпер + кнопка на всю
   ширину). Тач-таргеты ≥40px, без горизонтального скролла на 360px.

## Часть B — Контакты и адрес на лету при оформлении (фронт + backend)

### Backend (`api.optparts.kz`)

1. **`User.phones: string[]`** — несколько телефонов. Колонка `simple-array` (default пусто).
   - `UpdateProfileDto` принимает `phones?: string[]` (каждый — валидный телефон, напр. `@Matches`).
   - Ответы `/api/auth/me` и `/api/auth/profile` включают `phones`.
2. **`Order`** — новые nullable-поля: `recipientName varchar(150)`, `recipientPhone varchar(32)`,
   `customerComment text`.
   - `CreateOrderDto`: `recipientName?`, `recipientPhone?`, `customerComment?`.
     Правило: при `deliveryType='delivery'` — `recipientName` и `recipientPhone` обязательны;
     при `pickup` — опциональны.
   - `OrdersService.create` сохраняет эти поля в заказ.
3. **Миграции.** Файлы-миграции по конвенции проекта (`src/migrations/1700000000021-*`,
   `…022-*`). ВАЖНО: на текущей БД `migration:run` не отрабатывает (таблица `migrations` пуста,
   схема велась через `synchronize`) — новые колонки добавляются на dev-БД напрямую
   (`ALTER TABLE`) тем же DDL, что в миграции. Миграции нужны для будущего прод-деплоя.
4. **Опционально (вне scope сейчас):** показ `recipientName/phone/comment` в админской вкладке «Заказы».

### Frontend (`front`)

5. **`api.ts`:**
   - `addressesApi.create(token, body)` → `POST /api/addresses`; `addressesApi.setMain(token, id)`.
   - `ordersApi.create` body расширяется: `recipientName?`, `recipientPhone?`, `customerComment?`.
   - `AuthUser` и `UpdateProfileRequest` получают `phones: string[]`.
6. **Профиль (`Profile.tsx`):** управление списком телефонов — добавить/удалить несколько; сохранение
   через `updateProfile({ ..., phones })`.
7. **Чекаут (`Checkout.tsx`):**
   - Блок **«Получатель»**: имя (префилл `firstName + lastName`), **выбор телефона из сохранённых**
     (`user.phones`) + опция **«＋ добавить телефон»** прямо здесь; новый телефон и выбирается для заказа,
     и дописывается в профиль (`updateProfile`). Комментарий — опционально.
   - Блок **адреса**: сохранённые (радио, как сейчас) + инлайн-форма **«＋ Добавить адрес»**
     (title/city/street/postcode) → `addressesApi.create` → адрес добавляется в список и сразу выбирается,
     без ухода со страницы.
   - `createOrder` отправляет `recipientName`, `recipientPhone`, `customerComment`, `addressId`.
   - Валидация на фронте: при доставке имя+телефон обязательны (кнопка disabled).

## Часть C — Мобильный проход по покупательскому флоу

Пройти и починить адаптив: `Header`, поиск/офферы (Часть A), `Cart`, `Checkout` (Часть B), `Profile`.
Критерии: нет горизонтального скролла на 360px; тап-таргеты ≥40px; корректное стекирование колонок;
sticky-итог в чекауте не перекрывает контент; формы вводимы на узком экране.
Мобилку затронутых страниц (офферы, чекаут, профиль) делаем прямо в A/B; отдельно правим `Header` и
`Cart`. Финальная проверка — вживую в браузере на мобильном вьюпорте (playwright resize + скриншоты).

## Исполнение — параллельные worktree

- **WT‑A** (front): `OfferCard.tsx`, `OffersList.tsx` — офферы + ручной ввод количества + максимум + мобилка.
- **WT‑B‑be** (api): `User.phones`, `Order` поля, DTO, `OrdersService`, миграции.
- **WT‑B‑fe** (front): `api.ts`, `Checkout.tsx`, `Profile.tsx` — контакты, адрес на лету, телефоны, мобилка.
  Кодируется против контракта из B‑be (поля зафиксированы в этом спеке).
- **WT‑C** (front): `Header.tsx`, `Cart.tsx` — мобильные фиксы + финальная кросс-флоу проверка.

**Владение файлами (без пересечений):** A→OfferCard/OffersList; B‑fe→api.ts/Checkout/Profile;
C→Header/Cart; B‑be→api-репозиторий. WT‑B‑be мержится до WT‑B‑fe. Порядок БД-колонок — после merge B‑be
(`ALTER TABLE` на dev-БД).

## Тестирование

- Backend: unit-тесты сервисов (jest, мок-репозиторий) на новые поля заказа и обновление `phones`.
- Front: тест-раннера нет → `tsc --noEmit` + `npm run build` + живой прогон в браузере (desktop + mobile
  вьюпорт) через playwright.
- Приёмка: сортировка/бейдж «Выгодно»; ручной ввод количества с клампом и показом максимума; чекаут
  с контактами и адресом на лету создаёт заказ с сохранёнными полями; мобилка без горизонтального скролла.

## Открытые вопросы

- Формат/валидация телефона (маска) — минимально `@Matches(/^\+?[0-9 ()-]{7,}$/)`; UI-маска опционально.
