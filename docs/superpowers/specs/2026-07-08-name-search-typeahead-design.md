# Поиск по названию детали с автоподсказом (typeahead)

Дата: 2026-07-08
Статус: дизайн утверждён, готов к плану реализации

## Проблема

При вводе в строку поиска названия детали (например «Свеча») пользователь должен
попадать в нужную категорию каталога с раскрытой подходящей группой. Сейчас механизм
`GET /api/search/global` (mode = `name`) уже классифицирует запрос и возвращает категории,
но сопоставление имени с категорией — наивный подстрочный фильтр:

`src/catalog/services/global-search.service.ts:69-72`
```ts
const needle = q.toLowerCase();
base.name = { categories: categories.filter((c) => c.name.toLowerCase().includes(needle)) };
```

Из-за этого:
- «Свеча» (ед.ч.) **не находит** «Свечи зажигания» (мн.ч.) — морфология;
- опечатки, транслит («svecha»), синонимы не работают;
- ищется только по названиям категорий, не по подгруппам.

## Решения (утверждено с пользователем)

- **Поведение:** живой автоподсказ (typeahead) — дропдаун под строкой поиска по мере ввода.
- **Глубина подсказок:** категории + подгруппы (группы из дерева PartsIndex).
- **Матчинг:** стемминг (русский) + курируемые синонимы + фаззи (Levenshtein); индекс в памяти.
- **Наполнение индекса:** крон **раз в месяц** + материализация в таблицу БД; при старте индекс грузится из таблицы (0 запросов к PartsIndex).
- **Язык:** пока только `ru` (колонка `lang` в схеме заложена на будущее).

## Архитектура

Четыре изолированных блока, каждый с одной задачей и тестируемым интерфейсом:

```
[Cron: NameIndexBuilder — раз в месяц]  ──тянет──▶  PartsIndex (categories + group trees)
        │                                            через существующий CatalogCacheService
        ▼
[catalog_name_index — таблица в БД]  ◀── материализованный плоский снимок
        │
        ▼ (загрузка при старте + после каждого прогона крона / ручного rebuild)
[NameSearchIndex — сервис, индекс в памяти]
   • нормализация (lowercase, ё→е, транслит, стемминг)
   • синонимы (курируемая карта в коде)
   • фаззи (Levenshtein) как fallback
   • ранжирование
        │
        ├──▶ [GET /api/search/suggest]  ──▶  фронт: dropdown (Header.tsx)
        └──▶ используется также в global-search mode=name (единый резолвер)
```

Существующий `GET /api/search/global` (mode=`name`, сценарий «нажал Enter») переключаем
на тот же `NameSearchIndex`, чтобы логика матчинга была в одном месте.

## Компоненты

### 1. Таблица `catalog_name_index` (TypeORM entity + миграция)

Плоский снимок категорий и подгрупп. Не источник правды — крон перестраивает целиком.

| колонка | тип | назначение |
|---|---|---|
| `id` | pk | |
| `kind` | `'category' \| 'group'` | тип записи |
| `catalogId` | text | id категории PartsIndex (напр. `lamps`) |
| `groupId` | text null | id подгруппы (для `kind='group'`) |
| `name` | text | отображаемое имя («Свечи зажигания») |
| `parentName` | text null | имя категории для групп (контекст в подсказке) |
| `lang` | text | язык записи (пока всегда `ru`) |
| `norm` | text | нормализованная+стеммленая форма для матчинга |
| `updatedAt` | timestamptz | наблюдаемость / чистка устаревшего |

Индекс БД по `(lang, kind)`. Обновление — транзакцией upsert + удаление записей со старым `updatedAt`.

### 2. Крон `NameIndexBuilder`

`@Cron`, дефолт `0 0 1 * *` (раз в месяц, 1-го числа в полночь), интервал переопределяем через
`.env` (по образцу `ORDER_STATUS_POLL_CRON` в `src/orders/order-status.cron.ts`).

Шаги прогона:
1. `catalog.listCategories(lang)` → 1 запрос, все категории.
2. Для каждой категории `catalog.groups(catalogId, lang)` → дерево групп; плоско разворачиваем
   в записи `kind='group'`. Идёт через `CatalogCacheService` — при живом кэше сети почти нет.
3. Считаем `norm` каждой записи общей функцией нормализации (тот же модуль, что и матчинг).
4. Транзакцией пишем в `catalog_name_index`, чистим устаревшее.
5. Вызываем `NameSearchIndex.reload()`.

Плюс защищённый admin-эндпоинт `POST /api/catalog/name-index/rebuild` для ручного обновления,
не дожидаясь месяца.

Бюджет PartsIndex: ~1 + (число категорий) запросов на прогон, только при промахах кэша.
Раз в месяц — пренебрежимо мало относительно лимита 1000. При старте приложения индекс грузится
из таблицы (0 запросов); пустая таблица → ленивый первичный билд.

Наблюдаемость: логировать число категорий/групп и промахов кэша.

### 3. Сервис `NameSearchIndex` + модуль `name-normalize.ts`

Чистая логика без сети, покрывается unit-тестами.

**Нормализация** — `normalize(text) → string[]` (токены), одна функция для крона (`norm`)
и для запроса:
- lowercase, `ё→е`, убрать пунктуацию, схлопнуть пробелы;
- транслит латиница→кириллица по таблице (`svecha→свеча`, `lampa→лампа`);
- разбить на токены, отбросить стоп-слова (`для`, `и`, …);
- стемминг каждого токена.

**Стемминг** — чистый JS-порт Snowball (russian), без нативных бинарников (безопасно для
прод-сборки `node dist/main`). `свеча/свечи/свечей/свече → свеч`.
Запасной вариант, если JS-порт окажется проблемным при интеграции: встроенное отсечение
частых русских окончаний прямо в модуле (проще в поддержке, чуть грубее на редких формах).

**Синонимы** — курируемая карта в коде (`synonyms.ts`), ключи по стеммленой форме, правится
без миграций, растёт по логам реальных запросов:
```
свеч   → [свеч зажиган, свеч накал]
тормоз → [колодк, диск, суппорт]
дворник→ [щетк стеклоочистител]
фильтр → [фильтр воздушн, фильтр маслян, ...]
```

**Ранжирование** — score по каждой записи индекса:
1. точное совпадение стеммленого токена — высший вес;
2. префиксное совпадение;
3. попадание через синоним;
4. фаззи-fallback (Levenshtein ≤1–2 по длине слова) — только если точных/префиксных мало;
5. бонусы: `kind='category'` выше `group`; более короткое имя выше (специфичнее).

Отдаём топ-N (по умолчанию 8), категории и подгруппы вперемешку с пометкой типа, порог
отсечения от мусора.

**Интерфейс:**
```ts
suggest(query: string, lang = 'ru', limit = 8): NameSuggestion[]
reload(): Promise<void>   // перечитать из таблицы; зовёт крон и rebuild-эндпоинт

// NameSuggestion = { kind, categoryId, groupId?, name, parentName?, score }
```

### 4. Endpoint `GET /api/search/suggest`

`GET /api/search/suggest?q=&lang=ru&limit=8` — в `SearchController` (SearchModule), рядом с
прогрессивным поиском, чтобы все «поиск»-ручки были в одном контроллере.
- min 2 символа, иначе `[]`;
- тонкая обёртка над `NameSearchIndex.suggest()`, без сети → единицы мс;
- ответ: `{ query, suggestions: NameSuggestion[] }`.

### 5. Фронт — `Header.tsx`

- дебаунс-ввод (~200 мс) → `searchApi.suggest(q)` через TanStack Query (хук `useSuggest`);
- дропдаун под строкой: иконка (категория/подгруппа), имя, для подгруппы серым `parentName`;
  клавиатура ↑↓/Enter/Esc + клик мышью;
- выбор → навигация:
  - категория → `/catalog/:categoryId`;
  - подгруппа → `/catalog/:categoryId?group=:groupId` (CategoryPage раскрывает нужную группу;
    `GroupTree` уже принимает активную группу — прокинуть из query);
- Enter без выбора из списка → текущий `/search?query=` (mode=name), теперь с умным матчингом.

### 6. Логирование спроса

Расширить `search_log.queryType` enum на `'name'` (миграция) и логировать name-запросы с числом
подсказок. Запросы с 0 подсказок — сигнал, какие синонимы дописать. Делает карту синонимов
самоулучшающейся.

## Тестирование

- **Unit (TDD):** таблица кейсов вход→ожидаемый топ для `NameSearchIndex` на фикстуре индекса
  (без БД): `свеча / свечи / svecha / свеча зажигания / сеча(опечатка) / тормоз / фильтр` и т.д.
- **Модуль нормализации:** стемминг форм, транслит, стоп-слова.
- **Крон:** билд из мока PartsIndex → корректная плоская запись в таблицу; повторный прогон
  чистит устаревшее.
- **Endpoint:** min-длина, форма ответа.

## Вне рамок (YAGNI)

- глобальный поиск по названиям конкретных деталей (только категории + подгруппы);
- мультиязычность (только `ru`; колонка `lang` заложена, en — позже);
- персонализация / история подсказок;
- вынесение синонимов в БД/админку — карта живёт в коде.
