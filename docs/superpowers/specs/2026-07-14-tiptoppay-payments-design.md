# Приём онлайн-оплаты через TipTopPay

**Дата:** 2026-07-14
**Статус:** утверждён к реализации

## Цель

Клиент оплачивает заказ картой **до того**, как заказ уходит поставщикам. Сейчас
`OrdersService.create()` создаёт заказ и тут же размещает его у поставщиков — оплаты нет вовсе.

Дополнительно: привести сайт в соответствие требованиям TipTopPay к сайту мерчанта, иначе
эквайринг не пройдёт модерацию.

## Принятые решения

| Решение | Выбор | Почему |
|---|---|---|
| Способ приёма карты | Виджет TipTopPay (`widget.js`) | Карта вводится в iframe TipTopPay, мы её не видим → PCI SAQ-A вместо SAQ-EP с ежеквартальными ASV-сканами. 3-D Secure виджет ведёт сам. |
| Схема платежа | Одностадийная (`charge`) на полную сумму | Проще. Возврат при сбое поставщика делает менеджер вручную из админки. |
| Момент создания заказа | Сразу, статус `awaiting_payment` | Вебхук всегда знает, к какому заказу относится платёж; недооплаченные заказы видны в админке. |
| Частичный сбой поставщика | Заказ `partially_placed`, деньги списаны полностью, возврат — вручную менеджером | Явное решение заказчика. |
| В скоуп v1 | возврат из админки, авто-отмена неоплаченных заказов | |
| Вне скоупа v1 | сохранённые карты (токены), рекуррентные платежи, автоматический возврат | |

## Архитектура

Новый модуль `src/payments/`. `OrdersService` о TipTopPay не знает; связь — через вызов
`OrdersService.placeWithSuppliers(orderId)` из `PaymentsService` после подтверждённой оплаты.

### `TipTopPayClient` (`payments/tiptoppay.client.ts`)

Обёртка над `https://api.tiptoppay.kz`:

- Basic Auth: `PublicId` : `ApiSecret`.
- Заголовок `X-Request-ID` (uuid) — идемпотентность на стороне TipTopPay, кэш 1 час.
- Ответы вида `{ Success, Message, Model }`.
- Методы: `refund(transactionId, amount)`, `get(transactionId)`.
  (`charge` инициирует виджет на фронте, серверный `charge` не нужен.)

Ключи из `.env`: `TIPTOPPAY_PUBLIC_ID`, `TIPTOPPAY_API_SECRET`.
`ApiSecret` не логируется и никогда не уходит на фронт.

### Сущность `Payment` (таблица `payments`, 1:1 с заказом)

| поле | тип | смысл |
|---|---|---|
| `id` | uuid | |
| `orderId` | uuid FK | заказ |
| `invoiceId` | varchar unique | номер счёта для TipTopPay и клиента |
| `amount` | decimal(12,2) | сумма к оплате, снимок `Order.totalAmount` |
| `currency` | varchar | `KZT` |
| `status` | varchar | `pending` → `paid` / `failed` / `refunded` / `partially_refunded` |
| `transactionId` | varchar null | id транзакции в TipTopPay |
| `cardLastFour` | varchar(4) null | для админки и карточки заказа |
| `cardType` | varchar null | Visa / Mastercard |
| `refundedAmount` | decimal(12,2) | сколько возвращено (0 по умолчанию) |
| `failReason` | text null | причина отказа банка |
| `paidAt` | timestamp null | |
| `raw` | jsonb null | сырой payload вебхука |
| `createdAt`, `updatedAt` | | |

### Сущность `PaymentEvent` (таблица `payment_events`)

Журнал вебхуков: `id`, `type` (`check`/`pay`/`fail`/`refund`), `invoiceId`, `transactionId`,
`body` (jsonb), `hmacValid` (bool), `processedAt`.

Нужна для двух вещей:

1. **Идемпотентность.** TipTopPay ретраит вебхуки. Повторный `Pay` с тем же `TransactionId`
   не должен второй раз отправить заказ поставщику.
2. **Аудит.** Разборы с банком и расследование попыток подделать платёж (`hmacValid: false`).

### `OrderStatus`

Добавляется одно значение: `AWAITING_PAYMENT = 'awaiting_payment'`, label «Ожидает оплаты».
Остальные статусы не меняются — детали платежа живут в `Payment`, а не в статусе заказа.

## Поток оплаты

### Эндпоинты

| метод | назначение | доступ |
|---|---|---|
| `POST /api/payments/init` | по `orderId` создаёт/возвращает `Payment` (`pending`), отдаёт фронту `publicId`, `invoiceId`, `amount`, `accountId`, `description` | владелец заказа |
| `POST /api/payments/webhook/check` | предавторизационная проверка | публичный, HMAC |
| `POST /api/payments/webhook/pay` | деньги списаны — **триггер размещения у поставщиков** | публичный, HMAC |
| `POST /api/payments/webhook/fail` | отказ банка | публичный, HMAC |
| `POST /api/payments/:orderId/refund` | возврат (полный/частичный), тело `{ amount, reason }` | менеджер/админ |
| `GET /api/payments/:orderId` | статус платежа | владелец / менеджер |

### Шаги

1. `POST /orders` — создаёт заказ и снимок цен, статус `awaiting_payment`,
   **не размещает у поставщиков** и **не чистит корзину** (клиент мог закрыть вкладку).
2. Фронт: `POST /payments/init` → открывает виджет TipTopPay в режиме `Single`.
   Карта и 3-D Secure — целиком внутри iframe банка.
3. TipTopPay шлёт вебхук **`Pay`**. Проверяем `X-Content-HMAC`, находим `Payment` по `invoiceId`,
   ставим `paid`, пишем `PaymentEvent`. Если такой `TransactionId` уже обработан — отвечаем `200`
   и ничего не делаем.
4. **Только теперь** запускается размещение: группировка по поставщикам, `placeSupplierOrder`
   по каждой группе. Здесь же чистится корзина и пишется аналитика `partnerProducts.recordOrder`.
5. Итоговый статус заказа считает `aggregateOrderStatus()`. В неё добавляется одна ветка:
   если **все** под-заказы `FAILED` → заказ `cancelled` (сегодня функция в этом случае вернула бы
   `partially_placed`, что неверно — размещено ничего не было). Менеджер делает возврат из админки.
   Частичный сбой → `partially_placed`.
6. Вебхук `Fail` → `Payment.failed` + `failReason`. Заказ остаётся в `awaiting_payment` —
   клиент может оплатить другой картой, `init` вернёт тот же `invoiceId`.

### Ответ вебхуку

**Всегда `200 OK` с телом `{"code": 0}`**, даже при внутренней ошибке — любой другой ответ
TipTopPay считает сбоем и ретраит. Поэтому порядок такой: сначала фиксируем факт оплаты в БД и
пишем `PaymentEvent`, потом работаем с поставщиками. Если размещение упало с исключением —
деньги уже получены, заказ виден в админке со статусом ошибки, менеджер жмёт существующий
`retry` или делает возврат.

**Источник правды об оплате — вебхук, а не редирект браузера.** Клиент может закрыть вкладку
сразу после 3DS — заказ всё равно уйдёт поставщикам.

## Безопасность

- **HMAC вебхуков.** `HMAC-SHA256(raw body, ApiSecret)` в base64, сравнение с заголовком
  `X-Content-HMAC` через `crypto.timingSafeEqual`. HMAC считается по **сырому телу**, поэтому в
  `main.ts` включается `express.json({ verify })` для сохранения `rawBody` — **только** для
  префикса `/api/payments/webhook`, остальные роуты не трогаем.
  Не совпал HMAC → `403` + `PaymentEvent{ hmacValid: false }` + громкий лог (это попытка
  подделать платёж).
- **Сумма никогда не берётся с фронта.** `/payments/init` считает её из `Order.totalAmount`.
- **Данные карты не проходят через наш бэкенд** — их обрабатывает iframe TipTopPay.

## Крон: авто-отмена неоплаченных заказов

Заказы в `awaiting_payment` старше **30 минут** переводятся в `cancelled`. Иначе таблица
заполнится брошенными корзинами. Интервал — константа в коде.

## Фронтенд

### Оплата

`Checkout.tsx`:

1. «Перейти к оплате» → `POST /orders` → `orderId`.
2. `POST /payments/init` → параметры виджета.
3. Ленивая загрузка `widget.tiptoppay.kz/bundles/widget.js` (хук `useTipTopPay`),
   вызов `widget.charge(...)` в режиме `Single`.
4. `onSuccess` → `/success?order=<id>`. Страница **опрашивает `GET /payments/:orderId`** до
   терминального статуса: вебхук может прийти на пару секунд позже редиректа. Показываем
   «Платёж принят, размещаем заказ у поставщиков…» → итог.
5. `onFail` → остаёмся на чекауте, показываем причину отказа и «Попробовать другой картой».
6. Клиент закрыл виджет → заказ висит в `awaiting_payment` с кнопкой «Оплатить»,
   авто-отменяется кроном через 30 минут.

`OrderDetails.tsx` и «Мои заказы»: блок платежа — статус, сумма, последние 4 цифры карты,
кнопка «Оплатить» для неоплаченных.

### Админка

В карточке заказа — блок платежа и кнопка **«Возврат»** (полный / частичный, с указанием
причины) → `POST /payments/:orderId/refund`. Кнопка активна только для `Payment.status = paid`
или `partially_refunded`.

Сейчас все юридические ссылки в футере ведут на заглушку `/about` — модерацию это не пройдёт.
Нужны реальные страницы, доступные **без авторизации**.

### Новые страницы (`front/src/pages/legal/`, роуты + ссылки в футере)

| страница | роут | содержание |
|---|---|---|
| Публичная оферта | `/offer` | предмет договора, порядок заказа и оплаты, сроки поставки, права сторон, реквизиты продавца |

## Тестовый режим

Существующий `settings.getOrderMode() === 'test'` сохраняется: в тест-режиме используется
тестовый терминал TipTopPay, а размещение у поставщиков по-прежнему пропускается
(`isTest` на заказе и под-заказах).

## Тесты (TDD — сначала падающий тест)

- `tiptoppay.client.spec.ts` — Basic Auth, `X-Request-ID`, разбор `{Success, Message, Model}`,
  обработка `Success: false`.
- `payments.webhook.spec.ts` — валидный HMAC проходит; битый → `403` + `hmacValid: false`;
  **повторный `Pay` с тем же `TransactionId` не размещает заказ второй раз**; ответ всегда
  `200 {"code":0}`.
- `payments.service.spec.ts` — успешная оплата запускает размещение; полный отказ поставщиков →
  заказ `cancelled`; частичный → `partially_placed`; сумма берётся из `Order.totalAmount`,
  а не из запроса; refund увеличивает `refundedAmount` и переводит статус в `refunded` /
  `partially_refunded`; возврат больше остатка отклоняется.
- `orders.service.spec.ts` — правка существующих: `create()` больше **не** размещает у
  поставщиков, оставляет заказ в `awaiting_payment` и не чистит корзину. Существующие тесты
  на это упадут — так и задумано.
- `payments.cron.spec.ts` — заказ в `awaiting_payment` старше 30 минут отменяется; свежий и
  оплаченный — нет.

## Выкладка

1. Миграция TypeORM: таблицы `payments`, `payment_events`, новый статус заказа.
2. Бэкенд: `npm run build` → `npm run migration:run` → `deploy/deploy.py backend`.
3. Фронт: `deploy/deploy.py frontend`.
4. В личном кабинете TipTopPay прописать URL вебхуков (делает заказчик):
   - `https://api.optparts.kz/api/payments/webhook/check`
   - `https://api.optparts.kz/api/payments/webhook/pay`
   - `https://api.optparts.kz/api/payments/webhook/fail`
5. Прогон на тестовом терминале и тестовых картах 3-D Secure → замена ключей на боевые.

## Открытые вопросы

- `TIPTOPPAY_PUBLIC_ID` / `TIPTOPPAY_API_SECRET` ещё не переданы — до их получения в `.env`
  лежат плейсхолдеры, интеграция проверяется на тестовом терминале.

## Порядок работ

Бэкенд (клиент → вебхуки → размещение после оплаты → крон → refund) → фронт (виджет, статусы,
админка) → юридические страницы → прогон на тестовом терминале → боевые ключи.
